# 공용가계부

커플이나 가족이 함께 쓰는 공용 가계부. 같은 장부에 같이 기록하고, 누가 얼마를 냈는지 자동으로 정산합니다.

- 프론트엔드: React (Vite) + TypeScript
- 백엔드: Node.js (Express) + TypeScript
- DB: MySQL (운영은 MySQL 호환 TiDB Cloud Serverless)
- 배포: Vercel (프론트엔드, 백엔드 각각 별도 프로젝트)

## 주요 기능

### 기록하기

- **빠른 입력**: 대시보드에서 금액·카테고리·메모·날짜만 넣고 바로 기록. 수입/지출 모두 지원
- **카드 문자 붙여넣기**: 카드 승인 문자나 네이버페이 결제 알림을 붙여넣으면 금액·가게·날짜·결제수단을 자동으로 채움
  - 신한·KB국민·삼성·현대·롯데·하나·우리·BC·NH, 한 줄로 붙은 문자, "가맹점:/결제금액:" 형식 지원
  - 누적 사용액·체크카드 잔액은 결제 금액으로 보지 않고, 승인 취소 문자는 경고
  - 문자 원문은 브라우저에서만 해석하고 서버로 보내지 않음
- **카테고리 자동 추천**: 메모를 쓰면 예전에 같은 메모(또는 같은 가게)로 고른 카테고리를 자동 선택. 기록이 없으면 가게 이름 사전으로 짐작 (스타벅스 → 카페/간식)
- **템플릿 원탭 입력**: 자주 쓰는 지출("스타벅스 아메리카노 2개")을 템플릿으로 저장해 한 번 탭으로 오늘 지출로 기록. 잘못 눌렀을 때 5초간 되돌리기
- **결제수단**: 카드 / 현금 / 네이버페이. 마지막으로 쓴 결제수단을 기억해 기본으로 선택
- **영수증 사진 첨부**: 지출마다 사진 1장. 업로드 전에 브라우저에서 긴 변 1600px JPEG로 압축
- **공동 / 개인 지출 + 분담 비율**: 공동 지출은 1:1, 6:4, 7:3 등 낸 사람의 부담 비율을 지정. 개인 지출은 정산에서 빠짐
- **#태그**: 메모에 `#제주여행`처럼 쓰면 태그가 됨. 목록에서 태그를 누르면 그 태그로 검색
- 내역 수정·삭제, CSV 내보내기(이번 달 / 전체 백업)

### 찾기와 분석

- **검색과 필터**: 모든 달에서 메모·카테고리 검색어, 태그, 기간, 금액 범위, 종류, 카테고리, 결제수단, 작성자로 찾기. 결과 건수와 지출·수입 합계를 함께 표시하고, 결과에서 바로 수정·삭제
- **태그 칩**: 자주 쓴 태그를 건수·지출 합계와 함께 보여줘서 "이번 여행에 얼마 썼지?"를 한 번에 확인
- **월별 대시보드**: 수입 / 지출 / 남은 돈, 예산 현황, 공동 목표, 최근 내역
- **통계**: 지난달 대비 증감, 이번 달 Top 3 카테고리, 카테고리별 비교, 결제수단별 지출, 날짜별 지출 캘린더
- **연간 데이트 비용**: 데이트/기념일 카테고리의 월별 막대 차트, 총액·월평균·작년 대비, 가장 컸던 데이트 Top 5. 어떤 카테고리를 데이트로 볼지 직접 선택
- **연말 결산 리포트("우리의 2026")**: 한 해를 스토리처럼 한 장씩 넘겨보는 카드. 총지출, 달별 추이, 많이 쓴 카테고리, 자주 간 곳, 큰 지출, 데이트, 구성원별 지출, 저축 등. 탭·스와이프·키보드로 넘김

### 정산

- **N명 정산**: 이번 달 공동 지출을 기준으로 구성원마다 받을 돈 / 보낼 돈을 계산하고, "누가 누구에게 얼마"를 최대 (인원 − 1)번 송금으로 정리
  - 2명: 낸 사람이 지정한 비율만큼 부담, 나머지는 상대방
  - 3명 이상: 기본값(1:1)은 전원 균등 분할, 그 외 비율은 낸 사람이 그 비율을 내고 나머지를 다른 사람들이 균등 분할
- **더치페이**: 공동 지출 중 일부만 골라 그 자리에서 정산 완료로 표시. 고른 건들의 송금 안내를 미리 보여주고, 정산된 건은 월간 정산에서 빠짐

### 함께 쓰기

- 네이버 로그인, 가계부 생성, 초대 코드로 참여 (최대 6명)
- **"이거 사도 될까?"**: 10만원 이상 지출은 기록하기 전에 다른 구성원에게 물어볼 수 있음. 상대가 한마디와 함께 승인/거절하고, 승인되면 "샀어요!"로 바로 지출 기록

### 예산 · 고정비 · 목표

- **카테고리별 월 예산**과 초과 표시
- **고정비 / 반복 지출**: 매월 지정일(1~28일)에 자동 기록. 공동/개인 구분과 분담 비율도 그대로 적용
- **공동 목표 저축**: 목표 금액 대비 진행률, 적립 기록

### 앱 안 알림

알림은 대시보드를 열었을 때 맨 위에 보입니다. 배너는 닫으면 해당 기간에는 다시 뜨지 않고, "사도 될까?" 요청은 처리할 때까지 카드로 남습니다. (휴대폰 푸시 알림은 아직 없습니다)

| 알림 | 언제 |
| --- | --- |
| 고정비 결제 예정 | 결제일 하루 전 |
| 저축 리마인드 | 매달 15일 이후, 이번 달 적립이 없는 진행 중 목표가 있을 때 |
| "사도 될까?" 요청 | 다른 구성원이 물어본 요청이 대기 중일 때 |
| 연말 결산 | 12월(올해 결산), 1월(작년 결산) |

## 시작하기

### 1. MySQL 데이터베이스 준비

```sql
CREATE DATABASE accountbook CHARACTER SET utf8mb4;
```

스키마를 적용합니다.

```bash
mysql -u root -p accountbook < server/src/db/schema.sql
```

이미 쓰던 DB라면 이 단계는 건너뛰어도 됩니다. 서버가 시작될 때 `server/src/db/migrate.ts`가 새 기능에 필요한 테이블과 컬럼을 확인하고, 없는 것만 추가합니다.

### 2. 네이버 로그인 애플리케이션 등록

[네이버 개발자센터](https://developers.naver.com/apps)에서 애플리케이션을 등록합니다.

- **사용 API:** 네이버 로그인 (제공 정보: 이름, 이메일 — 이메일은 선택이어도 동작합니다)
- **서비스 URL:** `http://localhost:5173`
- **Callback URL:** `http://localhost:5173/api/auth/naver/callback`

등록 후 발급되는 Client ID / Client Secret을 다음 단계의 `server/.env`에 넣습니다.
Callback URL은 `.env`의 `NAVER_CALLBACK_URL`과 **글자 하나까지 같아야** 합니다.

### 3. 서버 실행

```bash
cd server
cp .env.example .env   # DB 접속 정보, JWT_SECRET, NAVER_CLIENT_ID/SECRET을 채워 넣기
npm install
npm run dev
```

`http://localhost:4000/api/health` 접속 시 `{"status":"ok","db":"connected"}` 가 나오면 성공입니다.

### 4. 클라이언트 실행

```bash
cd client
npm install
npm run dev
```

안내된 주소(기본 `http://localhost:5173`)로 접속해서 네이버로 로그인 → 가계부 생성(또는 초대 코드로 참여) 순서로 시작하면 됩니다.

### 5. 테스트

```bash
cd client && npm test   # 프론트엔드
cd server && npm test   # 백엔드
# 둘 다 npm run test:watch 로 파일을 고칠 때마다 다시 실행할 수 있다
```

- **프론트엔드** (Vitest + Testing Library, jsdom): 정산 계산, 카드 문자 해석, 카테고리 추천, 태그, 날짜·금액 표시 같은 로직과 검색·문자 붙여넣기·토스트 같은 컴포넌트 동작. 테스트 파일은 대상 파일 옆(`*.test.ts`)이나 `__tests__/` 폴더에 둡니다.
- **백엔드** (Vitest + supertest, `server/test/`): 실제 MySQL 없이 가짜 DB(`test/helpers/fakeDb.ts`)로 돌아갑니다. API 입력 검증, 권한 규칙("사도 될까?" 본인 승인 금지 등), 검색 조건 조립, 정산 응답, 구성원 확인 캐시, 고정비 자동 기록 중복 방지를 확인합니다. 가짜 DB는 등록되지 않은 SQL이 오면 실패하므로 예상 못 한 쿼리도 잡습니다. 테스트 코드 타입 검사는 `npm run typecheck:test`입니다.
- 서버와 클라이언트에 복사돼 있는 정산 코드가 서로 같은지도 백엔드 테스트가 확인합니다.

## 알아두면 좋은 설계 결정

- **금액은 정수(원 단위)로 저장합니다.** 실수(FLOAT) 오차를 피하기 위함입니다.
- **가계부는 최대 6명까지 참여할 수 있습니다.** 커플에서 시작했지만 가족·룸메이트도 쓸 수 있게 늘렸습니다. `server/src/routes/households.ts`의 `MAX_MEMBERS`로 조정합니다.
- **정산은 공동 지출만, 건별 분담 비율을 반영해 계산합니다.** 계산 로직(`server/src/utils/settlement.ts`)은 더치페이 미리보기를 위해 `client/src/utils/settlement.ts`에 같은 코드가 복사돼 있어서, 한쪽을 고치면 다른 쪽도 같이 고쳐야 합니다. 원 단위로 나눠떨어지지 않는 금액은 1원씩 나눠 얹어 합계가 항상 정확히 맞습니다.
- **DB 구조 변경은 배포만 하면 반영됩니다.** 서버 인스턴스마다 첫 요청 전에 `migrate.ts`가 앱 자신의 DB 연결로 테이블/컬럼을 확인하고 없는 것만 추가합니다(여러 번 실행해도 안전). 새 테이블이나 컬럼을 추가할 땐 `schema.sql`과 `migrate.ts`에 같이 넣습니다. 운영 DB 콘솔에서 SQL을 손으로 실행하다 앱이 쓰는 DB와 어긋났던 일이 있어서 이렇게 바꿨습니다.
- **"오늘"은 사용자 기기 시간 기준입니다.** 서버(Vercel)와 DB는 UTC라 한국 시간 오전 9시 전에는 날짜가 하루 어긋납니다. 그래서 템플릿 원탭 기록, 목표 적립, 고정비 D-1 알림 등은 클라이언트가 계산한 날짜를 씁니다.
- **고정비 자동 기록은 크론(cron) 없이 동작합니다.** 거래 내역/요약을 조회할 때마다 "아직 이번 달 치가 생성되지 않은 규칙"을 그 자리에서 생성합니다 (`server/src/utils/recurring.ts`). 동시에 여러 요청이 와도 한 번만 생성되도록 조건부 UPDATE로 먼저 선점합니다.
- **알림은 푸시가 아니라 앱 안 배너입니다.** 이메일/푸시 인프라 없이 바로 쓸 수 있는 선택이고, 앱을 열어야 보인다는 한계가 있습니다.
- **영수증 사진은 DB(MEDIUMBLOB)에 저장합니다.** 서버가 Vercel 서버리스라 로컬 디스크에 파일을 둘 수 없기 때문입니다. 거래 목록이 무거워지지 않도록 별도 테이블에 두고, 볼 때만 받아옵니다.
- **태그는 따로 저장하지 않고 메모에서 뽑습니다.** 메모를 고치면 태그도 저절로 바뀌고, DB 변경도 필요 없습니다.
- **네이버 OAuth는 서버가 전 과정을 처리합니다.** `/api/auth/naver`가 네이버로 보내고, `/api/auth/naver/callback`이 code를 토큰으로 교환해 프로필을 조회한 뒤 우리 JWT를 발급합니다. CSRF 방지용 `state`는 httpOnly 쿠키로 검증하고, JWT는 서버 로그·Referer에 남지 않도록 URL fragment(`#token=...`)로 프론트에 전달합니다. 콜백 URL이 Vite 프록시(5173)를 거치는 이유는 state 쿠키와 프론트가 같은 출처여야 하기 때문입니다.
- **사용자는 네이버 고유 ID(`users.naver_id`)로 식별합니다.** 이메일은 제공에 동의하지 않으면 없을 수 있어서 nullable입니다.
- **서버는 `tsx`로 TypeScript를 직접 실행합니다** (`npm run dev`). 배포용 빌드는 `npm run build`(tsc로 `dist/`에 컴파일) 후 `npm start`로 실행합니다.
- **`req.userId`, `req.householdId` 같은 값은 `server/src/types/express.d.ts`에서 Express의 `Request` 타입에 전역으로 추가**해뒀습니다. `requireAuth`/`requireHouseholdMember` 미들웨어를 거친 라우트에서는 캐스팅 없이 바로 씁니다.

더 깊이 있는 기능을 학습 삼아 직접 확장하고 싶다면 [docs/WORKFLOW.md](docs/WORKFLOW.md) 의 질문들을 참고하세요.

## 배포

현재 운영은 **Vercel**(프론트엔드 `client`, 백엔드 `server`를 각각 별도 프로젝트로) + **TiDB Cloud Serverless**입니다.

```bash
cd server && vercel --prod   # 백엔드 먼저 (API가 바뀐 경우)
cd ../client && vercel --prod
```

API 응답 형식이 바뀌는 변경은 백엔드 → 프론트엔드 순서로 이어서 배포합니다. DB 구조 변경은 백엔드 배포 후 첫 요청에서 자동으로 반영됩니다.
